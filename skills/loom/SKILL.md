# Loom（编排委派工程范本）

> 适用范围：仅 ZCode。依赖其 Agent（run_in_background）、SendMessage 双向通道与任务自动通知机制，其他环境不保证可用。

一份任务文档交给多个 agent 并行推进时的标准打法。铁律一句话：**主管不施工、专家不执行、施工的实例不验收自己的票。**

两个词严格分开用：**审查** = 判断代码写得对不对（专家）；**验收** = 跑起来看是不是真的对（主管判断）。全文的「终审」「复核」都归入这两个词之一，不另立环节。

## 何时用 / 不用

- 用：用户给出任务文档/交接单/计划，内含 ≥2 个可并行推进的工程任务；或用户明说「拆票」「编排」「委派」。
- 不用：单一小任务（直接做）；纯调研讨论（无施工）。

## 角色

| 角色 | 选谁来当 | 职责 | 绝不做 |
|---|---|---|---|
| 任务主管（本 skill 执行者） | 当前主模型 | 读文档、基线核查、确认票据、编排（执行方/实例/并行/资源分配）、环境基线、**验收判断**、**写回回报**、终局收尾、收尾汇报 | 施工；替子 agent 改代码 |
| 工程专家 | 可用 agent 中工程判断最强的一个；最好与主力执行不同模型族，审查才能看到执行者的盲点 | to-tickets 起草+写入（每票标出审查方式）、**审查**（标为「逐票审」的票每票一次 + 全部收进后整单一次） | 施工（保审查独立性）；写回回报；编排决策（用哪些 agent、开几个实例、怎么并行、何时换将——这要依据施工途中的实时产物灵活调整，而专家只看得到任务文档、看不见现场） |
| 主力执行 | 指令明确时干活又快又省的 agent（可多实例） | 施工票：写码、自测、提交；也可接**验收执行**（按主管指定的命令跑测试、红绿对照、截图，只交原始证据） | 验收自己施工的票（同一实例） |
| 替补 | 宿主内置的通用 agent（通常继承主管模型） | 可用即用作执行/调查 | — |

具体用哪些 agent，按用户环境里实际有的来定：用户另有 agent 名册或说明时以它为准，没有就按上面的「选谁来当」从可用 agent 里挑，并在简报里说明为什么这样分。只有一个可用 agent 时，各角色用它的不同实例，独立性按实例保证（见「审查、验收与回报」）。

开工前向用户**一段话简报角色安排，不等确认直接推进**——简报内容即分工约束：票据内容与依赖归专家，编排归主管，专家在票据上发挥、不越界。agent 描述不完全准：按实际产出换人（规则见「实例复用与换人」），收尾汇报各 agent 表现并指出与描述的偏差。

## 主流程

1. **读任务文档 + 基线核查**（只读）：分支头、环境（工具链、端口）、相关规格章节。意图读不懂或与规格冲突，先问用户，不挑字面解读。
2. **简报角色**（一段话，不停顿）。
3. **拆票**：派专家读 to-tickets 技能 + 任务文档，起草草案（只输出、不写盘）——草案只含**票据内容与依赖**（What / Blocked by / 验收标准 / 依赖图），凡涉执行方、实例数、并行拓扑的建议仅供参考，由主管重裁。主管逐票审：不设单独的验收票（回归要求并进最后一张施工票）、能否独立开工、审查方式标得对不对（见「审查、验收与回报」）、单次委派 ≤2 票结构、合并动作是否排除在票外。主管的意见和决定用 SendMessage 发回**起草的那个专家实例**，由它修改并写入；不另派新实例写入（新实例没见过草案和主管的修改，只能重拆一遍）。主管的意见只写改什么、为什么，不替专家重写票据正文。
4. **排程 + 基线**：TodoWrite 立任务台账（每票标注执行方与依赖）；建工作树、装依赖、构建、分配端口偏移——**基线不稳不派工**。
5. **扇出**：主管的第一件大事是把**同时就绪**（Blocked by 全清）的票据同一条回复里一起派出，各自独立的工作树与端口；同类票据同时到齐时按票数开同类 agent 实例——实例就是并行度。串行只在有真实冲突时才对（同一工作树/端口/共享文件），并行的成本只是多写几段派单，串行的成本是整段等待。例：三张互不依赖的施工票同时就绪 → 本条回复 = TodoWrite 更新 + 三个 Agent 调用，一票一个，并行回流（派单模板见 references/dispatch-template.md）。
6. **推进**：每笔回流更新台账、裁决（通过/返工/换人/上报）；可穿插派专家做代码审查票——审查循环按「审查编排」，换人按「实例复用与换人」。
7. **整单审查**：全部施工收进后，派专家对照任务文档审一次整单（不重审已通过逐票审查的票）；派单里列出哪些票是「并入整单」、还没审过细节。结论与轮次按「审查编排」。
8. **验收**：主管组织独立重跑 + 旧代码工作树红绿对照 + 截图核对；跑的活可派验收执行，通过与否由主管判断（见「审查、验收与回报」）。
9. **写回回报**：主管按任务文档的回报格式（handoff 技能）把审查结论和验收证据写回任务文档（写在哪按任务文档或仓库规矩）。
10. **终局**：loom 的产出是「可合候选」，不是「已合并验收」，合并前的完整检查由派活方另做。默认终态**不合并、不问、不等**：交付物停在各自分支上，分支清单、合并顺序、偶发失败的判读写进回报并贴在最终对话里，用户回来自行处置。
11. **收尾**：简短汇报各 agent 表现与描述偏差。

## 委派纪律

1. **异步优先**：Agent 一律 `run_in_background: true`。原则上禁止阻塞等待，除非委派工具整体不可用才退化用同步模式。
2. **等待 = 结束回合**：手头活干完即停止输出，结果以 task-notification 自动回流；禁止轮询、禁止预测未回流的结果。
3. **基线冻结**：委派后若继续输出，不得碰子 agent 在用的目录、分支、端口与任务基线——防破坏其在途工作。
4. **派单自带全部材料**：子 agent 与主管、彼此上下文不共享。派单必须写全：必读文件路径（含技能文件路径——子 agent 不继承主管的技能上下文）、环境情报、步骤、硬边界、回报格式，并写明**「有疑问走双向通道 SendMessage 问主管，禁止直接问用户」**。
5. **票量**：单次委派 ≤2 票；同类难度可开同类 agent 多实例并行。什么时候接着用原实例、什么时候新派，见下节。
6. **隔离并行**：互不依赖的票并行委派，各占独立工作树与端口偏移；可拉分支。

## 实例复用与换人

实例 = 一段会话上下文。**接着用** = SendMessage 发回原实例；**新派** = 再调一次 Agent。

**同一件事的连续几步，用同一个实例。** 既省钱（缓存命中），也因为它记得前面的事：

| 一条线 | 包括 | 用同一实例的好处 |
|---|---|---|
| 一套票 | 专家起草 → 主管意见 → 专家写入 → 整单审查 | 记得主管改过什么，写入的和审过的草案一致 |
| 一张票的审查 | 首审 → 复审 | 记得上一轮的阻塞清单，复审不另开审查面 |
| 一张票的施工 | 施工 → 返工 | 熟悉自己写的代码 |

不跨线复用：一张票的施工实例不拿去做另一张票，也不做本票的验收执行。

**新派实例**只在这几种情况：
- 需要独立性：验收执行不能用施工的那个实例。
- 原实例意外停止：先 SendMessage 唤醒续跑；唤不醒再新派，附接手材料（已完成的提交、在途的事、证据位置）。
- 换人（见下）。

**换人。** 主管看不到 agent 的上下文，不去推测它满没满、乱没乱，只看看得见的信号和固定规矩：
- **同一施工实例最多两次机会**：施工 + 一次返工。这次返工后的复审仍有「上轮没修好」的阻塞，就换另一种 agent 接手（用的是本票最后一轮复审），不再判断是上下文问题还是能力问题。
- **提前换人的信号**（都在产出里看得见）：返工回报写不出「这次改法和上次有什么不同」，或者绕回已被打回的改法；提交记录显示在同一块代码来回改、撤掉自己上一轮的改动；执行者自己停下报卡住。出现这些信号时，新开一个同种 agent 实例接手（多半是上下文被搅乱）。
- 接手材料必须写：试过哪些改法、各自为什么被打回、当前停在哪个提交。
- 换人不重置轮数（见「审查编排」）。

## 工作树与票据落点

- 工作树统一放**项目同级** `<项目名>-worktrees/<任务名>/`（历史遗留目录不管、不动）。
- 红绿对照的旧代码**另立工作树**；禁止在施工/验收目录 stash 或 checkout 旧文件。
- 票据与编排产物放 `<项目名>-worktrees/_tickets/<slug>/issues/`（`NN-slug.md` + `INDEX.md`，含共同约束节），不进主仓库。
- 主目录（用户环境、在跑服务）零接触；并行 e2e 各设端口偏移；全量回归在哪跑、谁跑，按任务文档。

## 审查、验收与回报

三件事各归一个角色，各有自己的独立性要求，不混用：

| | 审查 | 验收 | 回报 |
|---|---|---|---|
| 回答 | 代码写得对不对 | 跑起来是不是真的对 | 结果怎么记下来 |
| 谁做 | 专家 | 主管判断；跑的活可派验收执行 | 主管 |
| 防的是 | 思路盲点 | 自己给自己打分 | 弱化、粉饰 |
| 独立性 | 模型族不同：专家与执行者天然不同，主管无需另外安排 | **按实例算**：不能是施工的那个实例（同一段会话上下文）；同模型的新实例可以 | — |

- **不为换模型而换人**：「换模型族找盲点」只是审查的理由，不用于挑验收执行者。选验收执行者只看三点：工具够用（能跑 e2e / 开浏览器 / 看图）、报告可靠、没碰过这段代码的上下文。因质量问题被撤下施工的 agent 不派验收执行。
- **验收执行只交原始证据**：命令、退出码、日志路径、截图路径，不下「通过 / 不通过」结论；结论由主管看证据给出。
- 审查方、验收方都不改被审 / 被验代码，发现问题交回施工方修复。
- **证据纪律**：退出码直接取（`cmd; echo $?`），禁止管道吃码（`cmd | tail` 会把失败吞成假绿）；核查日志勿截断（head/tail 截断会制造假结论）；证据必须关联提交——命令、退出码、日志路径、截图路径。
- **审查方式按票分级，由专家拆票时标出**：高风险的票（动外壳/撤销/数据/跨模块），以及后面有票要在它上面接着做的票，标「逐票审」；其余标「并入整单」，不做逐票审查，留到整单审查一起看。整单审查不省。
- 回报由主管写：数值不得弱化、偏离不得粉饰、只写角色不写 agent 名/真名；专家的审查结论原样引用（含风险与建议）。
- **推送、开 PR、合并不属于 loom 的流程**：任务文档或仓库规矩怎么写就怎么办，都没写就不做。

## 审查编排

主管安排的每轮专家审查——首审、返工后的复审——按此管理。

**轮数按票算，不按人算**：一张票最多**首审 1 次 + 复审 2 次**，换人接手也不重新计数（否则换人就成了绕开上限的办法）。「并入整单」的票，整单审查就是它的首审；整单审查里的每条阻塞都注明属于哪张票，之后按票返工、复审、计轮数。找得回原施工实例就发回它改，找不回按换人处理。

- **只有「打回」才返工**：专家结论为「通过」即结束审查，风险与建议原样写进回报，不为它们再派一轮。
- **复审发回做首审的同一专家实例**（SendMessage），附上一轮的阻塞清单，写明「这是复审，只核对这些阻塞」（派单形状见 references/dispatch-template.md「复审票」）。
- **复审的每条阻塞由专家贴标签**：「上轮没修好」「修复带出来的」「本轮新发现」（复审中只有四类严重问题能算新发现的阻塞：数据丢失、改错、安全漏洞、用户看到的结果和实际不一致）。
- **主管照标签决定，不自己推测**：

| 复审结论里的阻塞 | 说明什么 | 主管怎么做 |
|---|---|---|
| 全是「上轮没修好」 | 执行者没做到 | 返工；同一施工实例已用完两次机会就换人（见「实例复用与换人」） |
| 有「修复带出来的」 | 改法或设计不对，换执行者没用 | 停下这张票，上报派活方 |
| 有「本轮新发现」 | 新发现的严重问题（上面四类之一） | 停下这张票，上报派活方 |

- **到限即停、上报派活方**：第二次复审仍是「打回」，或任何一轮给出「升级」，或出现上表中要上报的标签，就停下这张票报给派活方——附专家结论、已修了什么、还剩什么，由派活方决定（继续、换人或拆分）。
- **不扩审查面**：不要自己追加审查面（如「再请专家全面过一遍」）；只有改动范围变了，才重新首审。

## 反模式

❌ 委派后阻塞等待 ｜ ❌ 轮询/催促未回流的 agent ｜ ❌ 预测未回流结果 ｜ ❌ 替子 agent 修代码 ｜ ❌ 派单让子 agent「有问题问用户」｜ ❌ 单次塞 3+ 票 ｜ ❌ 子 agent 在途时动它的基线 ｜ ❌ 未经用户拍板合并 ｜ ❌ 审查-返工死循环（到限不上报）｜ ❌ 为换模型族而换验收执行者 ｜ ❌ 让验收执行者自己下通过结论 ｜ ❌ 票里另设纯回归的验收票 ｜ ❌ 拆票的起草和写入派成两个专家实例 ｜ ❌ 换人后轮数从零算 ｜ ❌ 一张票的施工实例拿去做别的票 ｜ ❌ 凭猜测判断 agent「上下文满了」，而不看产出里的信号

## 工具与技能速查

- 工具：`Agent`(run_in_background) 委派 · `SendMessage` 双向通道/唤醒/续跑 · `TaskOutput` 备用主动拉取 · `TodoWrite` 台账 · `Bash`(background+取证) · `AskUserQuestion` 仅用于意图/规格冲突的裁决 · `Read`/`Grep` 证据核查。
- 技能：`to-tickets`（拆票方法，专家读）· `handoff`（任务文档与回报格式）· `code-review`（审查票执行方法，逐票与整单都用）。
